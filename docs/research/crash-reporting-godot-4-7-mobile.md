# Crash reporting for Godot 4.7 mobile — vendor and wiring

**Decision date:** 2026-08-13
**Target at decision date:** Glassvow, Godot **4.7.1**, iOS and Android
(desktop-aware). The exact project pin moved to **4.7.2** on 2026-08-21; the
vendor decision remains valid because the selected SDK supports Godot 4.5+.
**Status:** research decision; SDK integration remains a separate platform deliverable

## Decision

Adopt **Sentry for Godot 2.1.1 as the primary crash pipeline**, and retain **App Store Connect/Xcode Organizer and Google Play Android vitals as independent backstops**. Do not ship Firebase Crashlytics alongside Sentry.

This is the only compared route that has a first-party Godot SDK, explicitly supports Godot 4.5+, currently tests against **4.7.1**, captures Godot runtime/GDScript errors as well as native faults, and covers Android ANRs and Apple app hangs. It also gives the desktop ports one issue namespace. The current release is [Sentry Godot 2.1.1 (2026-08-03)](https://github.com/getsentry/sentry-godot/releases/tag/2.1.1); its repository declares the Godot/platform support matrix and includes 4.7.1 in the current test workflows ([repository](https://github.com/getsentry/sentry-godot/tree/2.1.1), [Android test workflow](https://github.com/getsentry/sentry-godot/blob/2.1.1/.github/workflows/test_android.yml)).

Firebase Crashlytics remains a viable no-cost fallback if Sentry's recurring service cost is rejected, but the credible Godot route is the community-maintained [`godot-x/firebase` 3.1.0](https://github.com/godot-x/firebase/releases/tag/3.1.0), not a Google-maintained Godot SDK. Its current Crashlytics bridge exposes initialise/collection, log, user ID, custom values and forced-crash methods, but no Godot error hook or non-fatal API carrying a GDScript stack ([Android bridge](https://github.com/godot-x/firebase/blob/3.1.0/source/android/firebase_crashlytics/src/main/java/com/godotx/firebase/crashlytics/FirebaseCrashlyticsPlugin.kt), [iOS bridge](https://github.com/godot-x/firebase/blob/3.1.0/source/ios/firebase_crashlytics/Sources/godotx_firebase_crashlytics.mm)). It therefore does not meet the GDScript observability requirement without maintaining an additional adapter.

Native consoles remain mandatory even with Sentry: they can expose failures before third-party SDK initialisation and platform health metrics that affect store standing. They are a complement, not a second embedded vendor.

## Recommended wiring

### Shared Sentry configuration

1. Pin the complete [2.1.1 release](https://github.com/getsentry/sentry-godot/releases/tag/2.1.1) under `addons/sentry`; configure the DSN in Project Settings and let the plug-in initialise before game scripts ([installation](https://docs.sentry.io/platforms/godot/)). Record the SDK version in dependency governance rather than following `latest`.
2. Set a stable `release` (application ID + semantic version) and store build number as `dist`; attach only low-cardinality fields such as platform, device tier and a non-player-identifying screen/encounter code ([release health](https://docs.sentry.io/platforms/godot/configuration/releases/)). Do not attach save state, seed, deck contents, localisation strings or player-entered text.
3. Use privacy-minimal defaults deliberately: `send_default_pii=false`; **change `attach_log` from its default `true` to `false`**; leave screenshots, scene-tree attachment and GDScript local variables off; do not set a user ID. Sentry documents that the default Godot log attachment can contain sensitive material, while screenshots are off and user information is not sent by default ([data collected](https://docs.sentry.io/platforms/godot/data-management/data-collected/), [options](https://docs.sentry.io/platforms/godot/configuration/options/)). Keep Android ANR and Apple hang capture on.
4. Use `before_send` to remove unexpected free text and bound noisy non-fatal events; document server-side retention and deletion access. Sentry's Godot SDK supplies the filtering hook ([sensitive data](https://docs.sentry.io/platforms/godot/data-management/sensitive-data/)).

### Android

Install the Godot Android Gradle build template, enable **Use Gradle Build**, and allow the Sentry export plug-in to inject its Android dependency ([Android configuration](https://docs.sentry.io/platforms/godot/configuration/android/)). For every production ABI/build ID, upload matching unstripped Godot/export-template and game-library symbols with `sentry-cli`; the official Godot 4.7 instructions explain the stable-template symbol archives and custom-template alternative ([Sentry symbolication](https://docs.sentry.io/platforms/godot/configuration/stack-traces/), [Godot Android crash symbols](https://docs.godotengine.org/en/4.7/tutorials/platform/android/resolving_crashes_on_android.html)). Keep Play Console symbol upload as a separate release step.

### iOS

The 2.1.1 build bundles Sentry Cocoa 9.24 and requires **iOS 15.0 or later** ([release repository/build configuration](https://github.com/getsentry/sentry-godot/blob/2.1.1/SConstruct)). That deployment-floor change needs product approval before integration. Export with dSYMs, upload the application dSYM and Sentry/Godot native debug files for the exact release, and retain the signed Xcode archive ([Sentry symbolication](https://docs.sentry.io/platforms/godot/configuration/stack-traces/), [Apple crash reports](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs)).

### Release proof

Before production enablement, use internal builds on real devices to prove one GDScript error, one deliberate native crash, one Android ANR and one iOS main-thread hang. The acceptance gate is a correctly grouped and symbolicated Sentry event **and** the corresponding native-console behaviour, with the sent payload inspected for the agreed privacy fields. A successful SDK initialisation is not crash-reporting proof.

## What the Firebase alternative would require

The plug-in currently declares Godot 4.7 stable, iOS 13+, Android API 24+, Firebase Apple 12.16 and Android Crashlytics/NDK 20.1.0 ([3.1.0 repository](https://github.com/godot-x/firebase/tree/3.1.0)). Integration means pinning its `addons`, `ios` and `android` artefacts; adding `GoogleService-Info.plist` and `google-services.json`; enabling the Android Gradle build; adding the Google Services and Crashlytics Gradle plug-ins; and enabling Core plus Crashlytics.

That README-level path is not sufficient for actionable native stacks. Android's Crashlytics NDK symbol upload is disabled until configured and requires build-ID-matched unstripped libraries; provided libraries such as a Godot export template need `unstrippedNativeLibsDir` or equivalent upload input ([Firebase NDK documentation](https://firebase.google.com/docs/crashlytics/android/get-started-ndk)). Apple's supported route requires the Crashlytics build/run script or an equivalent dSYM upload for every archive ([Firebase Apple setup](https://firebase.google.com/docs/crashlytics/ios/get-started)). Glassvow would also have to build and own a Godot error adapter, while still lacking Firebase iOS hang reports and a desktop Crashlytics SDK. These are the reasons not to select this route despite its zero licence price.

## Store privacy and safety declarations

The following is the **minimum configuration-specific answer for the proposed telemetry-only build**. It assumes no analytics SDK, ads, account/user ID, screenshots, logs, local variables, save data or player-entered content. Re-run both store questionnaires whenever those assumptions or the resolved native dependency graph changes.

### Recommended Sentry build

**Apple App Privacy:** declare **Diagnostics → Crash Data, Performance Data, Other Diagnostic Data**, plus **Identifiers → Device ID** for Sentry's random per-app/per-installation identifier. Mark them **not linked to the user's identity**, **not used for tracking**, and used for **App Functionality** and **Analytics**. Sentry states that mobile SDKs use a random app/install ID rather than IDFA or a persistent device ID, process data for monitoring, require disclosure, and name App Functionality and Analytics as the standard purposes ([Sentry mobile privacy](https://docs.sentry.io/security-legal-pii/security/mobile-privacy/)); Apple's category definitions put crash logs, hangs and technical diagnostics in those three Diagnostics types ([App Privacy details](https://developer.apple.com/app-store/app-privacy-details/)). If user identity or free text is later attached, add the corresponding linked data categories rather than reusing this answer.

**Google Play Data safety:** declare collection of **App info and performance → Crash logs and Diagnostics** and **Device or other IDs**; purposes **App functionality** and **Analytics**; collection **required** while always-on; data is processed off-device. Mark **not shared** only while Sentry is contractually acting solely as a service provider and no onward integration independently uses it—Google's rules exclude qualifying service-provider transfers but make the developer responsible for the answer ([Play form rules](https://support.google.com/googleplay/android-developer/answer/10787469), [Android data-type definitions](https://developer.android.com/privacy-and-security/declare-data-use)). State transport encryption and the privacy-policy deletion/request route only as actually configured in the selected Sentry region/contract. Sentry itself requires all transmitted types to be included in the Play form and privacy policy ([Sentry mobile privacy](https://docs.sentry.io/security-legal-pii/security/mobile-privacy/#google-play)).

### If Crashlytics is selected instead

**Apple App Privacy:** for Crashlytics 12.16 with no Analytics/custom keys/logs/user ID, declare **Diagnostics → Crash Data** and **Other Diagnostic Data**, **not linked**, **not used for tracking**, for **App Functionality**; the transitive Firebase Installations manifest additionally identifies **Other Diagnostic Data** for **Analytics**. These are the declarations in the versioned [Crashlytics privacy manifest](https://github.com/firebase/firebase-ios-sdk/blob/12.16.0/Crashlytics/Resources/PrivacyInfo.xcprivacy) and [Firebase Installations privacy manifest](https://github.com/firebase/firebase-ios-sdk/blob/12.16.0/FirebaseInstallations/Source/Library/Resources/PrivacyInfo.xcprivacy). Firebase separately documents always-collected crash stack/application state/device-and-OS data and usage-dependent custom keys, logs, free-text IDs and Analytics breadcrumbs ([Apple disclosure guide](https://firebase.google.com/docs/ios/app-store-data-collection#firebasecrashlytics)).

**Google Play Data safety:** declare **App info and performance → Crash logs and Diagnostics** and **Device or other IDs** (Crashlytics installation UUID and transitive Firebase installation ID), for **App functionality** and **Analytics**; always-on collection is **required**, off-device and encrypted in transit. `Not shared` remains conditional on the service-provider exception and no linked service. Firebase documents the exact automatically collected stack, app state, device metadata and identifiers, HTTPS transport, limited subprocessors/instruction-based transfers and developer deletion capability ([Firebase Play disclosure guide](https://firebase.google.com/docs/android/play-data-disclosure#crashlytics)). Add every category implicated by custom values, logs, user IDs or Analytics breadcrumbs. Crashlytics retains stack traces, extracted minidumps and associated installation identifiers for 90 days before removal begins ([Firebase privacy and security](https://firebase.google.com/support/privacy/#crashlytics)).

### Native platform reports

Using only Apple's and Google's operating-system/store reporting adds no third-party telemetry SDK to the binary, so it adds no third-party collection row to either form. The app still needs an accurate privacy policy and both store questionnaires for all of its own and other dependencies' practices. Platform diagnostic sharing is opt-in and governed by the platform reports described by [Apple](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs) and [Google Play](https://support.google.com/googleplay/android-developer/answer/9859174).

The game's premium one-price model and lack of launch IAP do not change these telemetry disclosures. No purchase or payment category is created by crash reporting. `en`/`zh-Hant` is irrelevant unless localised or player text is placed in logs, which this design prohibits.

## Open gates and residual uncertainty

1. **Sentry iOS deployment floor:** 2.1.1 requires iOS 15.0; confirm that this is within the product's supported-device policy before implementation ([build configuration](https://github.com/getsentry/sentry-godot/blob/2.1.1/SConstruct)).
2. **Apple privacy-manifest packaging:** the Sentry 2.1.1 Godot release must be probe-exported and inspected in an Xcode archive. The release contains prebuilt native frameworks, while Apple's rule makes the app responsible for valid privacy manifests and signatures for included third-party SDKs ([Apple third-party SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/), [privacy manifests](https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests)). Do not assume Godot export preserved a manifest; use Xcode's privacy report and App Store validation as the evidence gate. Perform the same preservation check for the Firebase plug-in if that route is revived.
3. **Versions and forms drift:** re-check the pinned SDK release notes, pricing and current App Store/Play questionnaire immediately before implementation and submission. This document fixes the decision facts at 2026-08-13, not a floating dependency policy.
